# БРИФ — Фронтенд (CQA)

## Твоя миссия + жёсткие ограничения
Строим интерфейс для оценки качества диалогов. **Ограничения не обсуждаются** (это требования ТЗ):
- **Чистый статик HTML/CSS/JS.** Его потом встраивают как HTML-компонент в Dynamics 365 (через iframe/HTML Web Resource). → **Никакого SSR, никакого Next.** Если очень хочешь React — только Vite со **статик-билдом**. Проще и надёжнее: ваниль + чуть **Alpine.js**.
- Всё общение с данными/моделью — **через наш бэк по REST** (ключи и CORS на бэке, фронт их не трогает).
- **Авторизации НЕТ.** Апелляцию и ревью показываем как **разные действия в интерфейсе** (две роли, без логина).
- Язык интерфейса — русский; контент диалогов бывает RU/KZ/EN.

## 4 экрана (в порядке приоритета)
**① Список диалогов** — `GET /api/dialogs`. Строки: `conversation_id`, канал (чат/звонок), язык, короткое превью. Клик → экран ②.

**② Диалог + Оценка** (ядро, вылизать) — два столбца:
- Слева: **транскрипт**. Реплики с цветом по роли (client/operator/bot/system) и таймкодом. Для звонков (`audio_url` есть) — **аудиоплеер**, клик по реплике = перемотка. База: [hyperaudio-lite](https://github.com/hyperaudio/hyperaudio-lite).
- Справа: **результат по каждому критерию** — название, вердикт/балл, вес, объяснение, и **ссылка-доказательство**, которая **прыгает к нужной реплике и подсвечивает её**. N/A — показать с причиной. Грубая ошибка — отдельный красный бейдж. Снизу — **итоги по секциям** и **общий балл**.
- Кнопка **«Оценить»** → `POST /api/score` → живой разбор (НЕ из кеша — жюри проверяет, что анализ настоящий).

**③ Редактор чек-листа** — `GET/POST /api/checklists`. Список критериев; добавить/править: название, секцию, тип (`Да-Нет` / `Да-Нет-N/A` / `шкала`), вес, разрешён ли N/A, ступени шкалы с подписями. Сохранить → конфиг обновился → переоценка берёт новый конфиг. **Это страховка на H23** (жюри вживую заменит один критерий — ты должен уметь это сделать через UI). Всё **data-driven**: критерии рисуются из конфига, ничего не хардкодь.

**④ Апелляция + Решение** — на оценённом критерии:
- «Оспорить» → выбрать критерий, комментарий, сохранить (`POST /api/appeals`).
- Вид проверяющего: спорная оценка + комментарий + фрагмент диалога → подтвердить/изменить + причина (`POST /api/reviews`) → итог пересчитывается.
- В карточке видно: **исходная оценка → решение → финал** (исходную НЕ затираем, кладём слоем).

## API-контракт (строй на этих моках, пока бэк не готов)
```
GET /api/dialogs → [{conversation_id, channel, language, turns, preview}]

GET /api/dialogs/{id} →
{ conversation_id, channel, language, audio_url,
  transcript:[{idx, timestamp, speaker, text}] }      // idx — для ссылок-доказательств

GET /api/checklists/{id} →
{ id, name, rounding:2,
  criteria:[{id, order, section, name,
             type:"bool"|"bool_na"|"scale"|"flag",
             weight, na_allowed, scale_max, scale:[{value,label}], guidance}] }

POST /api/score {dialog_id, checklist_id, provider} →
{ dialog_id, provider, total, gross_error,
  sections:[{name, points, max}],
  results:[{criterion_id, applicable, na_reason,
            verdict:"yes"|"no"|null, raw_score, scale_max,
            points, effective_weight, explanation,
            evidence:{turn_idx, timestamp, quote}}] }

POST /api/appeals {dialog_id, criterion_id, comment} → {appeal_id}
POST /api/reviews {appeal_id, decision:"confirm"|"change", new_verdict, new_score, reason}
      → {result: <такой же объект score с original/decision/final по критерию>}
```

## UX-musts (прямо влияют на оценку жюри)
- **Ссылка-доказательство ДОЛЖНА визуально прыгать к реплике** — это и удобство, и доказательство, что система реально читала ЭТОТ диалог (критерий «корректность процесса»).
- **Тумблер провайдера на виду** (Облако Gemini / Локальная Qwen3) — показываем гибрид (критерий «разнообразие архитектур»).
- Чисто, понятно, без лишних кликов (критерий «удобство»). Лоадеры и пустые состояния — обязательно.
- Весь процесс «выбрал диалог → оценил → увидел обоснование → оспорил → пересмотрел» должен читаться за 5 минут демо.

## Порядок работы
1. Моки по контракту → Экран ② (транскрипт + результат) — это сердце демо.
2. Экран ① (список).
3. Экран ③ (редактор чек-листа) — не откладывай, это H23-страховка.
4. Экран ④ (апелляция/ревью).
